# 2026-04-24_01_LCD_가로늘어짐제거_256x96_mono전환

## 1. 작업 목적
기존 ST7735S/ST7735SV 드라이버는 RGB565 컨트롤러 픽셀 단위로 외부 API를 노출하고 있었고, 이로 인해 컨트롤러 픽셀 1개를 켜면 실제 mono TFT 패널에서는 가로 3 dot × 세로 1 dot이 동시에 점등되어 텍스트와 이미지가 가로로 약 3배 늘어져 보이는 문제가 있었다. 이번 단계의 목적은 외부 App이 사용하는 좌표계를 패널 사양 그대로인 256×96 mono dot 좌표계로 통일하고, 가로로 인접한 mono dot 3개를 RGB565 1픽셀의 R/G/B subpixel로 packing하는 드라이버 내부 경로를 도입해 1 dot × 1 dot 출력을 가능하게 하는 것이다. 적용 범위는 ST7735S 드라이버와 ScreenManager이며, BatteryDisplay는 코드 적용까지 완료하되 모듈 폐기/이관 검토 중이라 시각 검증은 보류한다.

## 2. 수행내용

### 2.1 원인 분석
- 현상: 컨트롤러 RGB565 1픽셀을 켜면 실제 mono TFT 패널에서는 가로 3 dot이 동시에 점등되어 텍스트/이미지가 가로 약 3배로 늘어져 보임
- 원인 판단: ST7735S/ST7735SV의 RGB565 1픽셀 내부 R/G/B subpixel이 가로 인접한 mono dot 3개(KJC 2.25 inch, 물리 256×96)에 1:1 매핑됨을 Phase 0 캘리브레이션으로 확인

### 2.2 캘리브레이션
이번 단계에서는 컨트롤러 RGB565 subpixel과 mono dot의 실제 매핑 관계, 그리고 패널이 실제로 표시 가능한 가시 영역의 경계를 측정해 좌표계 도입에 필요한 최종 매크로 값을 확정했다. 이후 모든 단계의 변환식과 매크로는 여기서 정해진 값을 기준으로 한다.

세부 진행사항:

- 테스트: 좌측 상단에 R/G/B 단색 1픽셀(0xF800/0x07E0/0x001F)을 각각 출력해 mono dot 점등 위치 관찰
- `VIEW_X_MAX`/`VIEW_Y_MIN`/`VIEW_Y_MAX`를 인접값으로 swing해 패널 가시 한계 측정
- 인접 후보값(`VIEW_X_MAX=109`, `VIEW_Y_MIN=0`, `VIEW_Y_MAX=97`)은 모두 패널 밖/한계 초과로 기각 (상세는 plan Phase 0 결과 참조)
- 확정값:
  - subpixel 매핑 (`mono_x % 3`): 0→B, 1→G, 2→R (MADCTL=0x08 BGR 전제와 일치)
  - `ST7735S_VIEW_X_MIN=23`, `ST7735S_VIEW_X_MAX=108` (컨트롤러 86 px → mono 256 dot 가시)
  - `ST7735S_VIEW_Y_MIN=1`, `ST7735S_VIEW_Y_MAX=96` (96 line 전체 가시)
  - `MONO_USABLE_WIDTH=256`, `MONO_USABLE_HEIGHT=96` (패널 사양 100% 활용)

### 2.3 좌표계 전환
이번 단계에서는 외부 App이 사용하는 좌표 단위를 컨트롤러 RGB565 픽셀에서 패널 사양 그대로의 mono dot으로 통일했다. 좌표 변환은 드라이버 내부에서 4단계로 분리해 오프셋 중복 적용을 차단하고, RGB565 색상값이 외부로 노출되지 않도록 신규 매크로와 공개 API를 함께 정리했다.

세부 진행사항:

- 외부 API 좌표 단위를 `mono_x ∈ [0, 255]`, `mono_y ∈ [0, 95]`로 통일하고 RGB565 색상값은 직접 다루지 않음
- 신규 매크로: `MONO_WIDTH/HEIGHT`, `MONO_USABLE_WIDTH/HEIGHT`, `MONO_FRAME_BYTES`, `MONO_TO_CTRL_X(x)`, `MONO_SUBPX(x)`, `MONO_TO_RAM_X(x)`, `MONO_TO_RAM_Y(y)`
- 신규 공개 API: `ClearMonoBuffer`, `ClearMono`, `DrawMonoDot`, `FlushMono`, `FlushMonoRect`, `DrawChar3x5`, `DrawString3x5` (상세 시그니처는 plan 'Proposed API' 참조)
- mono → ram 변환은 4단계 공식(`mono_x/3` → `subpx` → `ram_x` → `ram_y`)으로 분리
- `RAM_OFFSET_*`/`VIEW_*_MIN`은 `ram_*` 산출 단계에서만 1회 적용 (이중 적용 방지). 범위 클램프는 드라이버 진입 시점에 1회만 수행

### 2.4 framebuffer / packing
이번 단계에서는 mono dot 3개를 RGB565 1픽셀에 묶어 보내기 위한 1bpp 풀 프레임버퍼와 packing 함수를 드라이버 내부에 추가했다. framebuffer를 shadow로 두고 read-modify-write로 동작시켜, 같은 컨트롤러 픽셀 안의 인접 dot 상태가 서로 덮어쓰여 사라지지 않도록 했다.

세부 진행사항:

- 1bpp 풀 프레임버퍼 `s_mono_fb[3072]` 추가 (256×96 / 8 = 3072 byte)
- `mono3_to_rgb565(r_on, g_on, b_on)` 내부 함수 추가: 같은 컨트롤러 픽셀에 속하는 mono dot 3개를 RGB565 1픽셀의 5/6/5 비트로 packing
- framebuffer를 shadow로 사용한 read-modify-write로 같은 컨트롤러 픽셀 내 인접 dot 상태 보존

### 2.5 Draw / Flush 구조
이번 단계에서는 Draw 계열 함수가 framebuffer만 갱신하고, LCD 송신은 별도 Flush 함수에서만 수행하도록 호출 규약을 분리했다. App은 한 화면을 구성한 뒤 마지막에 `FlushMono`를 1회 호출하는 표준 흐름을 따르며, 이로써 깜빡임 없는 한 장면 갱신이 보장된다.

세부 진행사항:

- 표준 화면 구성 흐름: `ClearMonoBuffer() → Draw*()... → FlushMono()` 1회 호출
- Flush 책임은 호출자(App). 드라이버 내부 자동 flush(타이머 주기 등)는 도입하지 않음
- framebuffer만 갱신, flush 안 함:
  - `ClearMonoBuffer(on)` — 표준 화면 구성 진입점
  - `DrawMonoDot(x, y, on)` — 1 dot 갱신
  - `DrawChar3x5(x, y, ch, on)` / `DrawString3x5(x, y, s, on)` — 텍스트
- LCD 송신 수행:
  - `FlushMono()` — 전체 송신 (화면 1회 갱신)
  - `FlushMonoRect(x0, y0, x1, y1)` — 부분 송신 (컨트롤러 픽셀 경계 자동 정렬)
- framebuffer + 즉시 flush:
  - `ClearMono(on)` — 테스트/디버그/긴급 전체 지움 전용

### 2.6 ScreenManager 적용 및 시그니처 강제 마이그레이션
이번 단계에서는 ScreenManager의 화면 출력 경로를 mono 표준 흐름(`ClearMonoBuffer → Draw* → FlushMono`)으로 일괄 전환했다. 동시에 `DrawChar3x5`/`DrawString3x5`에서 RGB565 컬러 인자를 제거해 구 호출이 빌드 단계에서 컴파일 에러로 강제 검출되도록 만들고, 드라이버 시그니처 변경과 호출부 11 사이트 수정을 단일 commit으로 묶어 적용했다. 적용 후 ScreenManager 전 화면에서 가로 늘어짐이 제거되고 깜빡임 없이 1회 Flush로 갱신됨을 육안으로 확인했다.

세부 진행사항:

- 화면 경로 전환: `Clear(SCREEN_BG_COLOR)` 단일 호출 → `ClearMonoBuffer(0U) + 함수 끝 FlushMono()` 표준 흐름
- DrawChar3x5/DrawString3x5 시그니처 교체: RGB565 컬러 인자(`fg_rgb565`, `bg_rgb565`) 제거 → `(mono_x, mono_y, ch/text, on)`
- 시그니처 변경 + 호출부 수정(총 11 사이트: ScreenManager_App.c 9건, BatteryDisplay_App.c 2건)을 단일 commit으로 적용 (중간 빌드 불능 commit 0건)
- 좌표 매크로 mono 단위 재계산:
  - ScreenManager: `SCREEN_TEXT_X` 2 → 6, `SCREEN_TEXT_Y` 2 (변경 없음), `SCREEN_BAT_LOW_Y` 12 (변경 없음)
  - BatteryDisplay: `TEXT_X` 3 → 9, `MARK_X` 59 → 177
- 검증 화면: BOOT/STANDBY/WAIT_CODECHIP/WAIT_CASSETTE/MEASURING/CALCULATING/RESULT_DISPLAY/POWER_OFF_NOTICE/BAT_LOW overlay 전 화면 깜빡임 없이 1회 Flush 갱신
- 십자선(가로 y=48, 세로 x=128)과 모서리 4점 (0,0)/(255,0)/(0,95)/(255,95) 모두 1 dot 폭 점등 확인
- BatteryDisplay는 좌표 재계산까지 적용했으나 시각 검증은 모듈 거취 결정 후로 보류

### 2.7 부분 송신 최적화 (dirty line bitmap)
이번 단계에서는 mono_y 라인 단위 dirty bitmap을 드라이버 내부에 도입해, 변경되지 않은 라인은 SPI로 송신하지 않도록 최적화했다. 공개 API 시그니처와 동작 의미는 그대로 유지되어 App 측 코드 수정은 0건이고, 동일 화면 재렌더 시 SPI 송신이 0 byte로 수렴한다.

세부 진행사항:

- mono_y 라인 단위 dirty bitmap `s_mono_dirty[12]` (96 bit) 추가
- `mono_fb_clear()` → 전 라인 dirty set
- `mono_fb_set_dot()` → 해당 mono_y 라인 dirty set
- `mono_flush_ctrl_rect()` → 송신 완료 라인 dirty clear (RAMWR 자동 진행 특성상 연속 dirty span 단위로 set_window/RAMWR 분할)
- 공개 API 시그니처/의미 변경 없음 → App 코드 수정 0건
- 효과: 첫 프레임 전체 송신 보장, 동일 화면 재렌더 시 SPI 송신 0 byte로 수렴, 부분 갱신 장면은 변경된 mono_y span만 송신
- SRAM: framebuffer 3072 byte + dirty bitmap 12 byte = **3084 byte**

### 2.8 Legacy 경로 정리
이번 단계에서는 RGB565 / 4bpp 기반 기존 출력 경로를 삭제하지 않고 legacy로 명시적으로 분리했다. 신규 App 경로에서 호출이 0건임을 확인해, mono 경로와 legacy 경로가 같은 화면에서 섞이지 않도록 경계를 명확히 했다.

세부 진행사항:

- `ST7735S_Drv_WriteFrame`, `ST7735S_Drv_Clear`, `gray_lut_565`, `st7735s_draw_pixel` 등 RGB565 / 4bpp 경로에 `[LEGACY]` 배너 + doxygen `@note` 부착
- 헤더에서 legacy API 선언을 별도 섹션 블록으로 분리
- `ST7735S_PANEL_WIDTH/HEIGHT`는 Init 단계 panel-wide clear/tuning에서 사용되므로 legacy 처리 제외 (주석으로 용도 명시)
- 신규 호출자 검증: `WriteFrame`/`Clear` 모두 USER/App 경로에서 호출 0건

### 2.9 Legacy 경로 완전 삭제
이번 단계에서는 2.8에서 보존만 해 둔 RGB565 / 4bpp legacy 경로를 소스 트리에서 완전히 제거했다. 롤백 가능성 0%로 판단되어 더 이상 두 경로를 공존시킬 이유가 없으며, 드라이버 표면을 mono 단일 경로로 축소해 코드 인지 부하를 줄이는 것이 목적이다. Init 단계에서만 쓰이는 내부 보조 경로(`st7735s_clear_black`, `st7735s_draw_tuning_pattern`, `ST7735S_PANEL_WIDTH/HEIGHT`)는 외부 렌더링 API가 아니므로 그대로 보존했다.

세부 진행사항:

- 사전 검증: USER/, Core/ 트리 전체 grep으로 삭제 대상 심볼의 외부 호출 0건 재확인 (`WriteFrame`/`Clear`/`st7735s_draw_pixel`/`gray_lut_565`/`ST7735S_DRV_WIDTH|HEIGHT|FRAME_BYTES`/`ST7735S_FRAME_OFFSET_X|Y`)
- 헤더 정리 (`ST7735S_Drv.h`):
  - `[LEGACY] RGB565 / 4bpp 경로` 섹션 블록 제거 (`ST7735S_Drv_WriteFrame` / `ST7735S_Drv_Clear` 선언 포함)
  - 4bpp 입력 전용 매크로 `ST7735S_DRV_WIDTH/HEIGHT/FRAME_BYTES` 제거
- 소스 정리 (`ST7735S_Drv.c`):
  - `ST7735S_FRAME_OFFSET_X/Y` 매크로 제거
  - `[LEGACY] RGB565 / 4bpp 경로 구현부` 배너 블록 주석 제거
  - `ST7735S_Drv_WriteFrame` 함수 본체 + 내부 `gray_lut_565` LUT 제거
  - `st7735s_draw_pixel` static 함수 제거 (유일 호출자였던 `ST7735S_Drv_Clear`와 함께 소멸)
  - `ST7735S_Drv_Clear` 함수 본체 제거 (코너 4점 마커 포함)
- 보존 대상 (삭제 아님): `st7735s_clear_black`, `st7735s_draw_tuning_pattern`, `ST7735S_PANEL_WIDTH/HEIGHT`, mono 표준 API 전체
- plan 문서 갱신: `설계문서/LCD/mono_tft_256x96_rendering_refactor_plan.md` Non-Goals 항목의 "4bpp `WriteFrame` 경로 삭제는 1차 범위 제외" 문구를 취소선 처리하고 Phase 2.9 완료 명기
- App 코드 변경 0건 (mono 표준 흐름만 사용하고 있어 영향 없음)
